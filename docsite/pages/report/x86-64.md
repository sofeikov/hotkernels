<p class="lede">Everything before this chapter was measured on one machine, an Apple M1 Pro. The kernels were then written a second time, for x86-64 with AVX2, against the same specs and the same judge. This chapter is what that showed: which ideas carried over, which did not, and what the same 23 kernels are worth on a processor where NumPy is a different opponent.</p>

## Written again, not translated

**The specs and the reference C are shared; the assembly is not.** A kernel's contract, its oracle and its correctness mode are the same files on both architectures. Its `kernel.s` is written from the idea and the proofs of the ARM64 one, not from its instructions, and an attempt rejected on one processor is not skipped on the other.

- **Machine.** Intel Core i5-14600KF, one performance core, Linux. Instruction set: the x86-64-v3 level (AVX2, FMA, BMI2), which the judge enforces and which `install()` asks the processor for.
- **The loop was the same.** [[ data.attempts_x86_64.total ]] logged attempts across the kernels written for x86-64 so far, the 23 of the first pass and those added from a second shortlist since: [[ data.attempts_x86_64.kept ]] kept and [[ data.attempts_x86_64.reverted ]] reverted. Of those taken to `judge compare`, [[ data.attempts_x86_64.verdicts.faster ]] came back significantly faster, [[ data.attempts_x86_64.verdicts.slower ]] significantly slower and [[ data.attempts_x86_64.verdicts.same ]] with no significant difference. The logs are beside each kernel, in `kernels/<name>/x86_64/attempts.md`.
- **Fewer attempts than on ARM64** ([[ data.attempts.total ]] there). The ideas were already known; what had to be found again was what this processor makes cheap and what it makes dear.

## A different opponent

**NumPy already has AVX2 loops for `argmax`, `clip` and `astype` here,** which were scalar or slow on the M1. And a chain of scalar additions costs one cycle per element on this core against three on the M1, while the caches deliver about the same. Two things follow.

- **Where NumPy is still scalar, the gains are of the same kind as on ARM64:** mask selection, masked assignment, `isin`, `histogram`, the searches.
- **Where the compiler's loop is already at the speed of memory, there is little left.** With the data in the second-level cache a plain copy takes 0.115 ns per 8 bytes and a running sum of `int64` in C takes 0.19. No kernel can do better than the copy, so `cumsum` on `int64` gains 1.18x over the C where the ARM64 kernel gains 4x.

## What carried over, and what did not

**The shapes carried over.** Reduce blocks and find the position afterwards; store without asking and advance by the count; build what one output adds to the last from the input alone; run many searches in step. So did every proof: where infinities land in a regrouped running sum, and which elements of a histogram need no edge correction.

**The instructions did not, and several ARM64 caveats went with them.**

- **`clip` is two instructions and one path.** `vmaxps a, b` returns its second operand when the two are unordered or equal, zeros of either sign included, which is exactly C's `a > b ? a : b`. With the bound first, a maximum and a minimum compute NumPy's result bit for bit for every ordered pair of bounds. The ARM64 kernel needs a path chosen by the bounds, a second look at data with negative zeros, and the floating-point status register.
- **A mask is 32 bits in one instruction.** `vpmovmskb` turns 32 mask bytes into a word, `tzcnt` and `blsr` walk its set bits, and a table indexed by a byte of it permutes eight elements to the front. The mask kernels have no weak spot near 10% density, and a mask byte is true when it is not zero, whatever its value.
- **`argmax` is one pass with a bounded second look.** The accumulators are never reset, so one compare per block says whether the block holds a new maximum, and only that block is looked at again. `vmaxps` loses a NaN, which `fmax` on ARM64 does not, so the NaN test is its own compare.
- **`histogram` has no divide per element.** A divide of four doubles takes eight cycles here. The proof only ever needed an estimate within a known distance of the true position, so the kernel multiplies by a scale computed once, and reads bin and fraction out of one conversion to fixed point.
- **The searches run 64 at a time, or 512.** Four probes share one `vgatherqpd`. The chain from one step of a search to the next is about thirty cycles and a gather can start every two or three, so sixteen searches in step, the ARM64 kernel's first width, left most of the processor idle.

**Some things this processor punishes** that the M1 does not: a 32-byte load or store that straddles two cache lines, and a store that lands just behind the data about to be read, which the processor mistakes for a store to it. Kernels that copy or accumulate into an output of the input's size load a block ahead of their stores for that reason.

## What it does not say

- **One machine again.** An Intel performance core. Gathers, which the search kernels use, are slow on some other x86-64 processors; nothing here was measured on one.
- **Four kernels beat the compiler by little:** `count_nonzero` on `float64`, `bincount`, `clip` on `float64` and the `uint8` cast. Shipping the C for them would be defensible.
- **Narrower than the number:** `isin` on int64 is fast only for test values from 0 to 32,767 here (on int32, added later, for any eight within 65,533 of each other), and with 64 needles against a very large array the searches are level with NumPy, because the judge repeats the same needles and a branching search learns them.
